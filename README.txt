Ниже — короткий, но “полный по сути” обзор: что делает приложение, где лежит логика и как всё связано. (это и переделать надо)

1) Что это за приложение
Blabify — Android-мессенджер на Firebase + Supabase:
Аутентификация: Firebase Auth (email+password).
Чаты/сообщения: Firebase Realtime Database.
Файлы: бинарники в Supabase Storage (публичные URL), метаданные и дерево папок — в Firestore.
Автосортировка файлов: юзкейс FileAutoOrganizer (domain), который читает текст по URL и раскладывает по подпапкам.

2) Пользовательский поток (экраны)
Splash (presentation/ui/Splash.kt) — показывает GIF и через ~4 сек открывает Autorization.
Авторизация (Autorization.kt) — signInWithEmailAndPassword; при успехе → ChatsActivity.
Регистрация (Registration.kt) — createUserWithEmailAndPassword; пишет имя в RTDB users/{uid}; при успехе → ChatsActivity.
Список чатов (ChatsActivity.kt)
Загружает чаты из RTDB chatRooms по ownerId == uid.
Создаёт чат → запись в RTDB + создаёт корневую папку в Firestore (folders/{folderId}, chatId = chatId).
Фильтр по «цветной метке» в Toolbar.

Открывает Chat с chatroomId.

Чат (Chat.kt)

Подписка на сообщения в RTDB: chatRooms/{chatId}/messages.

Отправка текста: sendMessageToUser(...).

Прикрепить файл (SAF + Supabase upload) → отправка «сообщения-файла» в RTDB + сохранение FileMeta в Firestore → запуск FileAutoOrganizer.

Дерево папок (Folders.kt)

Показывает корневые папки пользователя (createdBy == uid, parentId == null).

Раскрытие/сворачивание, загрузка детей по parentId.

Создание подпапок (запись в folders с parentId).

3) Где что лежит (данные и код)

Realtime Database

users/{uid} -> { name } (пишется при регистрации).

chatRooms/{chatId} -> ChatRoom.

chatRooms/{chatId}/messages/{messageId} -> Message.

Важно: именно как вложенная ветка chatRooms/{chatId}/messages — это следует из FirebaseUtil.getMessagesRef(chatroomId).

Firestore

Коллекция folders (вся иерархия в одной коллекции, дерево задаётся полем parentId):

folders/{folderId} -> Folder { id, name, parentId?, chatId?, createdBy, createdAt, ... }

folders/{folderId}/files/{fileId} -> FileMeta {...}

Supabase Storage

Бакет chat-files: путь /{uid}/{chatRoomId}/{fileName}; далее используется publicUrl.

Ключевые файлы

Data:

FirebaseUtil.kt — ссылки RTDB + имя текущего пользователя из RTDB.

SupabaseUploader.kt — загрузка в Supabase, возврат publicUrl.

SupabaseTextDownloader.kt — скачивание текста по URL (для классификации).

FirestoreRepositoryImpl.kt — операции с Firestore: дети по parentId, файлы в папке, транзакционный «переезд» файла между папками, BFS-потомки.

Domain:

usecases/FileAutoOrganizer.kt — координирует классификацию и перемещение.

api/FileClassifier.kt — контракт классификатора.

impl/RuleBasedClassifier.kt — простые правила (сейчас используется из Chat.saveFileMetaToFirestore).

Модели: ChatRoom, Message, FileMeta, Folder, AttachmentType, TreeItem.

Presentation/Adapters: ChatAdapter, MessageAdapter (текст/файл-сообщения), FolderAdapter (простые папки), TreeAdapter (дерево папок и файлов, загрузка детей по parentId + files).

4) Как работает автосортировка (по коду)

После загрузки файла и записи FileMeta в folders/{rootFolderId}/files/{fileId}:

В Chat.kt собирается список всех потомков корневой папки чата (FirestoreRepositoryImpl.getDescendantFolders BFS).

FileAutoOrganizer:

Берёт имена папок-кандидатов.

Если файл текстовый — скачивает содержимое (SupabaseTextDownloader).

Вызывает FileClassifier.classify(...) (сейчас RuleBasedClassifier).

Если уверенность ≥ 0.7 — ищет folderId по имени и перемещает запись файла транзакцией из folders/{root}/files/{fileId} в folders/{target}/files/{fileId}.

5) Точное соответствие конфигурации (Manifest/Gradle)

build.gradle.kts:

Supabase: BOM + storage-kt, postgrest-kt, Ktor Android.

Glide (GIF в Splash).

4) Почему «всё в одной коллекции» — это ок

Firestore всегда показывает все документы коллекции /folders одним списком (и корни, и подпапки)
 — так устроен UI консоли. Иерархию определяет поле parentId, а не «вложенность» в дереве консоли.
 Это не баг и не «грязь», просто такая модель данных (и она проще и надёжнее).


===================ПОЛИТИКА ПЕРЕМЕЩЕНИЙ (чёткие правила)============================
1. Скоринг (как сейчас, но честно)
Считаем совпадения по name (вес 1.0).
Плюсуем совпадения по предкам из path с затуханием (например: 0.7, 0.49, 0.343…).
Небольшой бонус глубине + 0.1 * level — только для тай-брейков внутри ветки.
Возвращаем сырое число score в ClassificationResult.

2. «Липкость» к ветке (branch affinity)
Как только файл впервые попал в ветку (ветка = ближайший ребёнок корня чата, напр. animals/puppy/...), мы считаем эту ветку «привязкой».
Пока файл в ветке P, рассматривать только потомков P (жёсткий фильтр кандидатов).
Исключение (перепривязка ветки): разрешаем переход в другую ветку Q только если
	новый счёт score(Q*) ≥ score(P*) + Δ, где Δ — заметный отрыв, напр. 0.8,
	и прошло как минимум T (например, 7 дней) с момента последнего перемещения (у тебя уже есть MOVE_COOLDOWN_MS),
	и отношение score(Q*) / score(P*) ≥ 1.5 (чтобы не «дёргало» из-за шума).
	Идеально — ещё и пользовательская подтверждалка в UI («переместить в другую ветку?»).

3. Неоднозначность
Если разница между 1-м и 2-м результатом < margin (например, 0.3) — ничего не делаем. Лучше пропустить, чем ошибиться.

4. Новые папки (например, появилась dogs/Max)
При появлении новых папок мы автоматически не перескакиваем ветку, пока нет сильных доказательств (см. п.2).
Но внутри текущей ветки продолжаем углублять файл при появлении новых подходящих подпапок.

ДЫРЫ


1. Файлы в Supabase — публичные
Загружаются в открытый бакет, ссылка постоянная.
→ Любой, у кого есть URL, может скачать.

2. Нет жёстких правил в Firebase

RTDB: доступ к chatRooms/messages не ограничен по participantIds.

Firestore: папки/файлы доступны без проверки createdBy.
→ Риск: чужие чаты и файлы можно читать/писать.

3. Доверие к данным с клиента

Message пишет userName и время с телефона.
→ Можно подделать имя и «отмотать» время сообщений.

4. Файлы в чат всегда в корень
Сначала кладутся в корневую папку чата, потом автосортировка двигает.
→ Если автосортировка сломается — всё застрянет в корне.

5. Подпапки работают, но не уникальны по имени
Классификатор ищет папку по названию.
→ Если есть одинаковые имена — файл попадёт «не туда». (фикс - папки по возможности размещаются на дальнем слое, а потом тогда 
остаются в папке, если не нашли подпапки, но файлы перемещаются по одной директории, просто по разным
уровням)

6. onActivityResult устарел
Используется для выбора файла.
→ Может падать/баговать на новых версиях Android.

7. Размер файла берётся неправильно
Через InputStream.available().
→ Это не реальный размер, может быть ноль или неверно.

8. MIME-тип файлов проверяется на глаз
Только «image/», «pdf», «excel/sheet».
→ Пропускаешь кучу форматов.

9. Подписка на сообщения не снимается
В Chat вешается ValueEventListener, но не убирается.
→ Утечки памяти и дубли сообщений.

10. Ошибки без обработки
Загрузка/сохранение файла и автосортировка — без try/catch.
→ Тихие сбои, рассинхрон RTDB ↔ Firestore.

11. Жёстко прошитые URL Firebase
Адрес RTDB «europe-west1» в коде.
→ Трудно переключать окружения (тест/прод).

----Возможное решение
Самая простая логика (понятная и безопасная)

- Авто-перемещение только при загрузке. Дальше — ничего само не ездит. Это снимает «страх потери». (Точка входа у тебя уже есть в Chat.kt после сохранения метаданных и запуска FileAutoOrganizer.)
- Если позже появилось место получше (создали новую подпапку, переименовали файл, добавили EXIF и т.п.), то файл:
не двигается сам, а попадает в список «Предложений» (review queue) с фразой «Предлагаем переместить → <папка> (уверенность 0.84)».
Окажется «в идеальном месте» в момент, когда ты нажмёшь “Применить” (по одному/пачкой).

- «Закреплённые» (pinned) файлы никогда не предлагаются к авто-перемещению. Порог уверенности и кулдаун нужны только для авто на загрузке — дальше всё через предложения. (В FileAutoOrganizer у тебя уже есть confidence; просто используем его как порог.)

- Чуть сложнее: что считать «появилось место лучше»

-- Мы не сканируем всё постоянно. Делаем пересмотр только на событиях (чтобы не грузить систему):
-- Создали/переименовали подпапку в ветке чата → пересчитать только эту ветку и сформировать предложения.
-- Изменились метаданные файла (например, появился EXIF у изображения (это как?)) → пересчитать конкретно этот файл.
-- Нажал кнопку «Пересортировать» на папке → считаем превью по этой ветке (dry-run), показываем *список предложений*.

Файл «застрял» в текущей папке? Он попадёт в «идеальное место», когда:

- появится триггер (одно из событий выше),
- классификатор даст вариант с уверенностью ≥ порога,
- ты подтвердишь предложение.
